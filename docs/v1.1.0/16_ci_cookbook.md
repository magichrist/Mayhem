# Plan 16 — CI cookbook

How to wire Mayhem into a pipeline, per provider. Everything here is generated by
`mayhem ci workflow` or is a description of what that generator emits; nothing is
a workflow file you should paste, because a pasted file will drift from the pins
the generator enforces.

## What is generated and what is only validated

This is the first thing to be clear about, because the honest answer is not the
one a CI integration usually claims.

| Artifact | Status |
| --- | --- |
| GitHub Actions workflow YAML | **Generated**, deterministically, from a pinned spec. Unit-tested byte-for-byte. **Never executed.** No workflow in this repository has ever run on GitHub. |
| GitLab CI component YAML | **Generated** the same way. Same caveat: never executed. |
| PR-check markdown summary | **Generated** and golden-tested against fixtures. Rendered by the CLI; a real `$GITHUB_STEP_SUMMARY` write has not happened. |
| Commit status POST | **Not implemented.** `CommitStatusPort` is an unbound protocol. `mayhem ci status` prints the status it *would* post and reports `posted: no`. |
| PR check evaluation | **Implemented and tested.** `evaluate_pr_checks` runs the real compile → proof → policy path over a plan and a topology. |
| Release-gate decision | **Implemented and tested.** `release_gate` fails closed. |
| ChatOps dispatch | **Implemented and tested** against a fake transport. **No Slack or Teams client exists.** |
| Terraform `mayhem_experiment` | **Implemented and tested** against a fake API. **No `terraform` binary has been driven**; the plugin handshake and state locking are not modelled. |

The rule this document follows: if a thing was not executed, this page says
"generated" or "validated", never "working".

## The two rules a generated workflow obeys

### 1. Every action tag and every base image is pinned

`actions/checkout@v4` is **refused** (`ci_surface.floating_action_ref`), and
`mayhem/sre:2.4` is **refused** (`ci_surface.floating_image_ref`). Only a
40-character commit SHA and a `sha256:` digest are accepted, and
`WorkflowSpec` has no field that can carry a tag — so there is no default to
forget to override.

The two pins this build ships:

```
actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
actions/setup-python@0b93645e9fea7318ecaed2b359559ac225c90a2b
```

They are constants in `controller/ci_surface.py`, and a documentation test asserts
this page still quotes the same SHAs — so a bumped pin without a bumped page
fails rather than rotting.

Why this matters more than it looks: an unpinned action is a gate whose
definition can change between the run that passed and the run that failed. You
are not comparing two evaluations of one gate.

### 2. No untrusted value is ever interpolated into a script

GitHub substitutes `${{ }}` into a `run:` block *before* a shell sees it, so
`run: echo ${{ github.event.pull_request.title }}` is remote code execution on
your runner, and a pull-request title is attacker-controlled.

The generator therefore emits `${{ }}` in exactly one place: the right-hand side
of an `env:` assignment, where it is a *value*. Inside `run:` it reads
`"$MAYHEM_PLAN_REF"` — a quoted shell expansion of an environment variable. Two
independent controls enforce this:

- the constructor refuses any untrusted value that is not a forge expression for
  the provider being rendered (`ci_surface.untrusted_value_in_script`; a GitHub
  expression in a GitLab component is refused too, because it is not a GitLab
  expression);
- `assert_script_containment` scans every rendered `run:` block for a `${{` and
  refuses the artifact with the same rule. This is the backstop for the day
  somebody edits the generated file by hand, and it is tested against exactly the
  injection it exists to prevent.

The two are deliberately redundant. Either one can be deleted by accident, and a
workflow generator is exactly the place where that mistake becomes remote code
execution on someone else's runner.

You do not choose a shell-quoting strategy. Mayhem does not build a shell command
out of untrusted text and then quote it carefully, because a careful quote for an
arbitrary future quoting bug is not a control.

## GitHub Actions

```bash
mayhem ci workflow \
  --provider github \
  --name mayhem-checks \
  --image ghcr.io/mayhemlabs/mayhem@sha256:<64 hex> \
  --check syntax --check blast_radius --check damage_budget \
  --release-gate \
  --env plan_ref='${{ github.event.pull_request.head.ref }}' \
  --env ticket='${{ github.event.pull_request.number }}' \
  --out .github/workflows/mayhem-checks.yml
```

The rendered job, in outline (the real file carries a header explaining each of
these):

- `permissions:` — `contents: read`, `statuses: write`, and nothing else. No
  package write, no deployment write, no `id-token`. Stated rather than assumed.
- `on: pull_request` with `types: [opened, synchronize, reopened]`. A fork PR runs
  with a read-only token and no secrets, which is why every step is permitted to
  do nothing but read.
- `actions/checkout@<40 hex>` with `persist-credentials: false`, so the token does
  not outlive the step.
- The checks run inside `docker run --network=none` against the digest-pinned
  image, with the working tree mounted read-only.

## GitLab CI

```bash
mayhem ci workflow \
  --provider gitlab \
  --name mayhem-checks \
  --image ghcr.io/mayhemlabs/mayhem@sha256:<64 hex> \
  --check syntax --check blast_radius \
  --out .gitlab/ci/mayhem.yml
```

Two differences you must know about, both stated in the generated file's header:

1. The trigger is a merge request, not a pull request.
2. **GitLab CI has no `uses:` key**, so the `ActionPin`s in your spec are *not*
   applied. There is nothing in GitLab CI for a commit pin to bind to. The
   generator says so in the rendered header rather than emitting plausible YAML
   that quietly drops them. The image *is* pinned, by digest, in the component's
   own `spec:` block.

Least privilege is the project's token scope, which this file cannot widen and
does not pretend to set.

## Jenkins, Buildkite, Argo Workflows, Tekton

**Not implemented.** `Provider` is a closed vocabulary of exactly `github` and
`gitlab`, and the docstring in `controller/ci_surface.py` gives the reason: each
of these needs a different trust model for "what ran before this step", and
emitting plausible-looking YAML for a provider nobody has reasoned about is how a
pipeline ends up with a gate that is decorative in exactly the environment it was
supposed to protect. They arrive as new `Provider` members, each with its own
pinning and containment rules.

## Running the checks in a job

```bash
mayhem ci check \
  --plan plan.json --graph topology.json \
  --sha "$GITHUB_SHA" --ticket "$MAYHEM_TICKET" \
  --pin plan_version=4.2.0 --pin policy_version=9 \
  --pin catalog_version=2.4.0 --pin agent_version=0.9.0 --pin runtime_version=1.11.0 \
  --summary "$GITHUB_STEP_SUMMARY" \
  --verdict-out verdict.json
```

**Exit non-zero unless every check passed.** The cases, and what each means:

| Situation | Checks report | Exit | Why |
| --- | --- | --- | --- |
| Plan unreadable, or no `--graph` | every check `UNKNOWN` | 5 (`SAFETY_REFUSAL`) | "mayhem could not ask" is not "nothing to report". A CI step that exits 0 because it could not reach its own control plane is a gate that fails open. |
| A check failed | that check `FAIL` with a finding | 5 | The finding is the compiler's own sentence, not a summary the surface wrote. |
| Everything passed | all `PASS` | 0 | — |

Two consequences of the current design that look like defects and are not:

- **No runtime adapter is bound**, so `validate_plan` skips the capability check
  and `capability_requirements` cannot be established. A plan naming a fault will
  therefore always fail `fault-compatibility`, with the compiler's sentence as the
  detail. Mayhem will not report a compatibility check as passing when it did not
  ask a runtime anything, and this command will not grow an `--adapter` flag to
  make that stop being true — an adapter is a live connection and a PR check should
  not open one.
- **The policy is the default one, not your repository's**, because a
  repository-supplied policy file is part of the change under test. A PR that
  loosened the policy would otherwise be checked against its own loosening.

## The summary

`mayhem ci summary` re-renders this from a verdict document, and
`mayhem ci status` prints the commit status a verdict would post. Three
properties are load-bearing in the summary:

- every check's outcome is printed verbatim, so `UNKNOWN` can never render as a
  tick;
- every coverage line reads `N of M` — a bare fraction is how an untested service
  reports 100%;
- the release-gate line is delegated to `blocking_reasons`, so the renderer
  cannot disagree with the engine about whether a release opens. It only prints
  the answer.

A summary over a verdict carrying **no checks at all** is refused
(`ci_surface.summary_without_verdict`): "every check passed" over zero checks is
a green tick on an absence.

A coverage *gap* rides on a passing check as a warning ("checkout has no
experiment covering PostgreSQL failure" is a true and useful thing to say about a
PR that is otherwise fine). Coverage that was **lost** is an error and fails: a
cell that was passed and no longer is a regression, not a gap.

## Posting a commit status

`mayhem ci status` prints the status a verdict *would* post and says plainly that
it posted nothing:

```
context:   mayhem/ci
state:     success
posted:    no
detail:    no commit-status port is bound: mayhem holds no forge token, so the status for 0123456789ab was not posted
```

`CommitStatusPort` is an unbound protocol. There are four ways to have no answer
from it — unbound, raised, answering `None`, answering in a wrong shape — and all
four produce the same finding, `ci_surface.status_unavailable`, with the control
plane marked **unreachable**. A DNS timeout is a fact about the network, not a
fact about the pull request, and the refusal is *not* a gate decision: the
pipeline verdict was already made, fail-closed, before this surface is reachable.

`UNKNOWN` maps to the `error` state, never `pending` and never `success`. `pending`
on a check that will never resolve is a status that sits on a pull request forever
while a required check is neither satisfied nor failing. `neutral` is not an
acceptable state at all — a shrug on a required check is a shrug a branch-protection
rule reads as a pass.

## The release gate

Attach resilience suites to deployments, dependency changes, and infrastructure
changes:

```python
request = ReleaseGateRequest(change=link, kind=ChangeKind.DEPLOYMENT, subject="checkout v2.5")
decision = release_gate(verdict, request, suites=[post_deploy_suite])
```

| Change kind | Suites owed |
| --- | --- |
| `DEPLOYMENT` | `resilience.post-deploy` |
| `DEPENDENCY` | `resilience.dependency-failure` |
| `INFRASTRUCTURE` | `resilience.infrastructure-drift` |

Every branch blocks. A required suite that did not report blocks. An `UNKNOWN`
suite blocks and is named with its reason. A `FAIL` blocks. A `PASS` with no cited
run cannot be constructed. And `ReleaseGateDecision` refuses to *be* an `allow`
without evidence refs and with every required suite passed-with-a-run — so
"allow" is not a value a caller reaches by leaving a field empty.

The plan's own worked example is in `tests/unit/test_ci_pipeline_gates.py`: v2.4 →
v2.5 with a 30% latency rise against a 20% tolerance blocks the release; a 15%
rise opens it; and a comparison that could not be graded is `UNKNOWN`, not a
pass.

## What a CI run may do (Phase 4)

A pipeline is not a lesser operator; it is an operator nobody is watching. Two
properties are structural, not documented:

**The identity is declared and never ambient.** A human principal inside a
pipeline is refused at `CIActor` construction (`ci_execution.ambient_privilege`).
A service account holding no role grant is refused too, and the refusal names the
role it needed. Authority is *resolved* through plan 09's `effective_roles`, never
asserted by the caller. Nothing in `controller/ci_execution.py` reads an
environment variable — mayhem does not discover who the pipeline is, the pipeline
declares it.

**The same execution intent, delegated.** `pipeline_run_authorization` *calls*
`require_execution_intent` rather than writing a second approval gate. That is
the whole claim: a CI approval and a terminal approval are the same approval
because there is one implementation.

**A run without an evidence link fails closed, never open.** Enforced in three
places, all under `ci_execution.run_without_evidence_link` and
`ci_execution.evidence_digest_mismatch`: a verdict citing no run is refused; an
envelope for a different run is refused; an envelope whose digest is not the
pin's is refused. And an authorization carrying no evidence still says no —
`opens_release` requires the link, so an unlinked authorization cannot open a
release even if one is constructed by hand.

The full refusal list for a pipeline admission, with the order it is enforced in:

| Rule | What it refuses |
| --- | --- |
| `ci_execution.actor_not_declared` | a blank principal id |
| `ci_execution.ambient_privilege` | a human principal inside a pipeline |
| `ci_execution.actor_without_role` | a service account holding no grant |
| `ci_execution.ticket_seal_broken` | a ticket edited after the seal, or one carrying shell syntax |
| `ci_execution.run_without_evidence_link` | no cited run, no envelope, or another run's envelope |
| `ci_execution.evidence_digest_mismatch` | an envelope that is not the evidence the pin names |

Identity, then authority, then approval, then seal, then evidence. A job with no
authority must not be able to ask for one by presenting a valid intent.

**Ticket refs are sealed.** The change references are bound to a digest at the
moment the check ran; a ticket edited between the check and the gate refuses.
Pass the check-time seal in as `seal=` and the authorization records
`seal_verified: true`; a caller that does not gets one minted on the spot and
`seal_verified: false`, because a seal verified against the link it was just read
from is a check that could not have failed.

## Rollout

1. **Validate in PR first.** Report only; do not make it required. The value is
   in seeing what your plan actually trips.
2. **Release gates second.** Once the PR checks are not noisy, attach the
   resilience suites to deployments.
3. **ChatOps and Terraform last.** Both are surfaces over engines that already
   exist; neither adds a decision.

## What this page does not claim

- **A fault pack is integrity-checked, not signed.** The pack format declares no
  public key, no signing algorithm, and no trust store, so there is nothing to
  check a signature against: `SIGNATURE_VERIFICATION_IMPLEMENTED` is `False` and
  is pinned by test. What *is* checked is the pack's SHA-256 content digest;
  authorship is an unverified claim. Any workflow above that installs a pack
  inherits exactly that guarantee, which is **integrity, not authorship**.
- **No workflow has run.** Generated, unit-tested, never executed.
- **No `verified-live` fault exists.** Zero of the catalog's entries are
  `verified-live`, and this stays true. Do not read "the catalog lists a fault"
  as "the fault has been demonstrated on a live system".
- **Nothing here suggests gating production on uncertified faults.** A check on
  an uncertified fault reports a *warning*, and the reason is in
  `check_gate._claim_warnings`: a check that is red on every PR until the entire
  catalog is certified is a check people learn to ignore. What is unrepresentable
  is the opposite — an uncertified fault *reported as certified* — which is
  refused at construction in `FaultClaim`. If you build a gate on top of these
  checks, gate on the certification state the check actually reported, not on the
  fault being in the catalog.
